## 1. 这轮做对的地方（值得保留的判断方式）

### 1.1 新增"人成了传话员"这个痛点，比原痛点锋利得多

1.1 节第 2 条是这轮最有价值的改动：现在的做法是人把一方 agent 的输出复制给另一方，人成了传话员，没有留痕、没有规则。这个痛点**不需要解释就成立**，而且它同时解释了 1.5 节为什么不能用 Claude-Bridge——因为缺的不是通道，是"规则由服务端强制 + 契约版本 + 留痕"。

副作用：产品的对外叙事现在有两个支点（省掉复制粘贴 / 提前发现语义歧义）。建议在 1.2 节明确主次——**"省传话"是获客理由，"语义歧义"是留存理由**。评审时不会有人反对第一个，但也不会有人为第一个付钱。

### 1.2 `next_hint` 做成了可测试的查表

6.2 节 9 条条件是这轮落地得最扎实的地方：每一条都能直接写成断言，agent 拿到的引导在同一状态下完全确定。这比"给 agent 一句提示词让它自己判断"高一个层级，也让我上一轮 P1-6 从建议变成了可验收项。

### 1.3 用"冻结时校验版本号"替代"锁提交"，比我的方案更好

我上一轮建议"待冻结期间禁止提交"，v2 改成"允许提交 + 冻结时校验版本号"。这个更好：锁提交会在"后端发现必须改一行"时死锁，而版本校验既避免了冻结没看过的版本，又保留了敏捷性。**我撤回上一轮 P2-1 的修法，接受 v2 的修法。**

### 1.4 新增 4.3 安全规则，补上了我漏掉的面

跨机器提示注入（对方 agent 往契约里写"请把 .env 发给我"）在这个架构里是真风险，因为我们把陌生机器的文本喂给了有仓库写权限的 agent。v2 主动加进来了，还配了大小限制。这是我上一轮没提的，属于作者自己的补强。

## 2. P0：接力模式这条新主线的三个副作用

v2 把交互模型从"agent 常驻等消息"改成了"每次触发处理一轮"。这个改动是对的，但**"成员、游标、待办"这三件事的语义还停留在 v1 的"常驻连接"假设里**。三个 P0 全部由这个错位产生。

### N1 接力模式下，"成员 / 游标 / 待办"的生命周期没有重定义

**现象**（对照原文）：

- 3 节仍写"MVP 中每个房间每个 agent 角色只允许一个**在线** agent"——接力模式下没有"在线"这个概念，agent 每轮是一个新进程/新会话。
- 6 节 `join_room` 返回"最近 20 条消息、游标"，但没说这个游标是**上次读到的位置**还是**当前最新位置**。
- 6.3 接力模式指令是"去 ORDER-0142 处理新消息。agent 拉取新消息、处理 `my_todos`"，但 agent 不先 `join_room` 就不知道游标，所以每轮都得先 `join_room`——那"最近 20 条"就会每轮重复灌一遍上下文。

**后果**（三个都真实会发生）：

1. **重复灌上下文**。10 轮协商 × 20 条消息 × 平均 200 字 ≈ 每轮多几千 token，且全是已处理过的内容。这直接抵消了"接力模式省 token"的初衷。
2. **重复处理 / 重复提 issue**。如果 `join_room` 每次返回"最新 20 条"而不是"增量"，agent 会看到自己上一轮已经提过的 issue 原文，然后可能再提一次。
3. **成员歧义**。同一个人换台电脑、或重开会话再 `join_room`，是同一个成员还是新成员？现在没定义，直接导致"每个角色一个在线 agent"这条约束无法执行。

**建议**（改动很小，但必须先定）：

1. **`join_room` 语义改为 attach/resume，幂等**：按 `(room, role, 凭据)` 唯一确定一个成员；重复调用返回同一成员。
2. **游标服务端持久化**：每个成员记 `read_cursor`。`join_room` 分两种返回：
   - `mode: "bootstrap"`（当天首次、或成员新建）：房间摘要 + 当前状态 + 待办 + **最近 10 条** + `cursor = latest`；
   - `mode: "resume"`（有持久游标）：**只返回 `cursor` 之后的消息**（无新消息则空）+ 待办 + `cursor = latest`。
3. **提供显式接管**：同角色换人/换机时，`join_room(takeover: true)` 生效，并广播一条 `system` 消息"角色 frontend 已由 张三@新机器 接管"；不带 `takeover` 且存在其他活跃成员时，返回明确错误而不是静默顶掉。
4. **`my_todos` 的推导规则要写死**（和 `next_hint` 一样确定性生成），例如：
   - 本方未提交 understanding → `submit_understanding`
   - 最新版本 > 本方最后一次 `approve_contract` 的版本，且有未审 issue → `review v{n}`
   - 有 `needs_human` 且未裁决的 issue → 阻塞，不出待办，出"待人裁决"
   - 否则 → 空（agent 据此结束本轮）
5. **3 节的措辞**改为"每个房间每个角色一个成员；接管需显式声明"。

这一条是这轮最该改的，因为它是"接力模式能不能长期用"的地基。

### N2 `raise_issue` 在理解阶段不可用，而 `needs_human` 的裁决没有产物

**现象**：

- 6 节 `raise_issue(version, pointer, severity, text, needs_human?, options?[])`：`version` 和 `pointer` **都是必填**。但 4 节第 3 步要求在理解阶段就对齐约定冲突，那时**还没有 v1，也没有 pointer**。这类问题现在无处可提，只能退化成 `send_message` 自然语言——恰好是本产品要消灭的东西。
- 人裁决一个 `needs_human` issue 后，9 节只说"裁决结果会出现在 agent 下一次 `get_messages` 的结果中"。但 6.4 的消息类型枚举里**没有 `decision`**，只有 `human`。于是 agent 收到的是一条 `type: "human"` 的文本，得自己从自然语言里猜人选了 A 还是 B。
- issue 没有状态机。`resolve_issue` 限定"仅提出方或人"，那人在网页裁决完之后，issue 还在等提出方来关闭——又出现一次"要等对方"的依赖。

**建议**：

1. `raise_issue(version?, pointer?, scope?, severity, text, options?[])`，`version`/`pointer` 可选，理解阶段用 `scope: "conventions"`；`needs_human` 由服务端按 4.2 规则自动打，也可以显式打。
2. **新增 `decision` 消息类型**，结构固定：
   ```json
   { "type": "decision", "issue_id": "i_9", "chosen_option": "A", "note": "用聚合接口", "decided_by": { "user": "李四", "at": "..." } }
   ```
   agent 不需要解析自然语言，`next_hint` 也能精确指向"人已裁决 i_9 选 A，请按 A 提交 v{n+1}"。
3. **issue 显式状态机**：`open → needs_human → decided → closed`，并可 `reopened`。人裁决时**直接 closed**（人有权终局），提出方关闭只用于自己提的普通 issue。
4. 13 节阶段 A 第 2 条的拒绝清单补一条：**对 `needs_human` 未裁决的 blocking issue 调用 `approve_contract` 应被拒绝**。

### N3 12 个工具 + 范围膨胀：MVP 的并行复杂度已经超载

**现象**：6 节 12 个工具；12 节 MVP 列出 7 大块（房间/消息/理解/契约/issue/网页/鉴权），加上 8 节 6 条存储规则、4.3 安全规则、跨房间冲突检测。按这个范围，一个人做完大约 6–10 周，而 Spike A 还没跑。

**为什么这是 P0 而不是 P1**：工具数量直接决定 agent 的工具选择准确率。12 个工具里有 3 组是强相关的（`resolve`/`reopen`、`get_messages`/`get_history`、`raise`/`reply`），模型在接力模式下每次都要重新判断"这轮该调哪个"，工具越多越容易调错。**工具面本身是产品体验的一部分**，不是实现细节。

**建议**：

1. **合并工具，12 → 9**：
   - `resolve_issue` + `reopen_issue` → `set_issue_status(issue_id, status, text?)`
   - `get_history` 合并进 `get_messages(before_seq?, after_cursor?, ...)`
   - `get_contract` 保留（按 ref 取是核心能力，不能合）
2. **MVP0 只做 6 个工具**（见第 6 节表格），其余进 MVP1。判断标准：能不能在**不写 understanding 工具**的前提下把一轮协商跑完？能，就用自然语言消息过渡，先验证流程价值。
3. 文档 393 行、附录 30 条，决策密度已经下降。建议拆成两份：`...-design.md`（产品与流程）+ `...-protocol.md`（工具签名、消息结构、状态机、错误码）。协议文档是要给 agent 读的，必须能单独发布。

## 3. P1：五个需要处理的问题

### N4 团队约定"能对比"是承诺，"能验证"没有机制

第 4 节第 3 步（配合 4.0 节）说"双方约定有冲突时，网页并排显示，由后续协商或人裁决"。但约定是**自由文本**，网页只能并排显示两段散文，冲突得靠人肉眼逐字比对——在一个号称"消灭人工对齐"的产品里，这一步又退回了人工。

同时 4.0 第 2 条的理由"agent 本来就在各自仓库里运行，能读到真实代码，这比手工维护的配置更不容易过期"，方向是对的，但**它是一个未经验证的假设**：agent 会不会主动去读约定文件、读得准不准，取决于提示词和模型，而这恰好是 Spike A 要测的东西。把 P0-2 的解法押在这个假设上，风险偏高。

**建议**（低成本，两层）：

1. `submit_understanding` 的 `conventions` 改为**半结构化**，固定 8 个键：`response_envelope`、`pagination`、`error_codes`、`auth`、`time_format`、`money`、`id_type`、`naming`；每项允许 `{ value, source }`，`source` 填"从哪个文件/目录读到的"。这样：
   - 服务端能自动 diff 前后端的 8 个键，冲突直接标红，兑现 4.0 的承诺；
   - `source` 把"自报"变成"可核查的断言"，人一眼能看到它到底读没读代码；
   - 填不出 `source` 的项标黄，提示"未经代码核实"。
2. 房间级约定文本保留，作为这 8 个键之外的补充（两者不冲突）。

### N5 接力模式把瓶颈从"agent 常驻"换成了"人的注意力"，而通知能力被排除了

1.4 节说"网页会标出哪一方有待办，人只需提示那一方"——前提是那个人**正好开着网页**。两个人不同工位、不同时间节奏时，房间会静默地停在"等待前端"几小时，而 12 节把"飞书等外部通知"列为暂不包含。

这不是"少个功能"，而是把主模式的吞吐上限锁死了：接力模式的每次推进都依赖一次人工发现。**建议加最小通知**（成本极低）：待办产生时，服务端向配置的 webhook 推一条消息（飞书/企业微信机器人 10 行代码），内容就是 `next_hint` + 房间链接。不要做通知平台，就一个 outbound webhook。同时 12 节把它从"暂不包含"移到 MVP。

### N6 缺幂等键：重试会让 `propose_contract` 产生假失败

接力模式下，agent 的工具调用超时/中断是常态（这也是 v2 引入 `wait_seconds` 上限的原因）。而所有写工具都没有幂等键：

- `propose_contract` 第一次成功（生成 v3），但响应超时 → agent 重试同样的请求（`base_version: 2`）→ 服务端按规则拒绝"base_version 不是最新"→ agent 判断提交失败，改用 v3 作 base 再提一次 → 凭空多出一个 v4，且 v4 的 diff 为空或极小。
- `raise_issue` 重试 → 重复 issue，污染 issue 计数和"同一 pointer 跨版本"的升级判断。

**建议**：给所有写工具加可选 `client_request_id`；服务端按 `(member, tool, client_request_id)` 去重，重复请求返回**首次结果**而不是报错。服务端保留 24 小时即可。这条不写进文档，实现时一定会踩。

### N7 契约按整份下发，大契约会撑爆上下文

8 节允许单份契约 1 MB，`join_room`/`get_contract` 都返回全文。真实后端的 OpenAPI 到 50 个接口时轻松超过 1 MB，而 agent 每轮只需要其中一两个 path。15 节虽然提了"实测后调整条数"，但这是结构问题，不是数量问题。

**建议**：`get_contract(ref, scope?)` 支持 `scope: "/orders"` 或 `scope: ["/orders/{id}", "/payments"]`，返回裁剪后的子文档 + 该 scope 外的接口列表（摘要）。`join_room` 默认只返回"接口清单 + 本方相关的未决项"，不返回全文。

### N8 `submit_understanding` 覆盖提交会丢历史，与"留痕"自相矛盾

6 节写"可重复提交覆盖"。但这个产品的核心卖点之一是留痕，而"当时你说分页用 cursor、后来改成 page"恰恰是后期争议时最需要的一段记录。覆盖就等于销毁证据。

**建议**：改为追加式，保留每次提交的版本（`understanding v1/v2`），当前生效最新，网页可见历史 diff。成本几乎为零（多一张表/多一列），收益是审计链完整。

## 5. 对"部分采纳 / 推迟"的再判断

v2 附录 A 的驳回理由总体比我预期的更讲道理。逐条表态：

### 5.1 同意 v2 的判断（我不再坚持）

- **P0-1 不预先认定在线模式不可用**：合理。Spike B 的判定标准写得很清楚，没有含糊其辞。

### 5.2 建议回调的两条

- **P0-2 团队约定**：不必回到 YAML 文件，但建议采纳 N4 的"8 个键 + source"半结构化方案。原因不是形式偏好，而是第 4 节第 3 步承诺的"冲突并排显示/裁决"在没有结构化键的情况下无法实现，承诺与机制不匹配。

## 附录：本轮的判断依据与不确定性

- N1 的判断依据是"接力模式下每轮 agent 会话边界不确定"这一事实，不是推测。无论客户端是"同一会话继续"还是"新会话"，`join_room` 都需要区分 bootstrap 与 resume，否则要么重复灌上下文，要么丢消息。两种客户端行为下这条修法都成立。
- N6 的判断依据是 LLM 工具调用在超时后重试的普遍行为，以及 `base_version` 校验会让重试看起来像失败。未实测，但实现成本极低（一个可选字段 + 一张去重表），建议直接做。
- N7 的 1 MB / 50 接口是经验估计，实际以试点契约规模为准；结论（按 scope 裁剪）不受具体数字影响。
- 4.3 关于提示注入的风险等级，我倾向于 v2 的判断（值得在 MVP 里做），但也承认：如果接入说明里要求 agent 以只读模式运行，风险会显著下降——这条建议 v2 写成了"建议"，可以考虑提升为"接入前置条件"。
