# 圆桌 Agent 自动交接设计（用户已确认，2026-10-27）

## 目标与使用方式

用户向房间中的一个 Agent 发任务后，Agent 可以主动把自己的最终结果交给另一位审查；有问题交回修改，审查通过或需要用户决策时 @我 并暂停。无需用户逐轮复制、转述、手动 @。本功能只讨论和审查，不自动进入写代码或执行部署。

典型流程：用户 @Codex 出方案 → Codex @DeepSeekHarness 审查 → DeepSeekHarness 提出具体问题并 @Codex 修改 → Codex 更新并再次交审 → DeepSeekHarness 审查通过，@我「方案已通过审查，可以确认进入开发」，停止自动交接。任一步如缺少必须由用户决定的信息，列出问题和建议选项后 @我，停止自动交接。

## 方案选择

1. 推荐：Agent 明确提出交接意图，服务端验证并调度。保留自由讨论，同时由程序保证目标、顺序、次数和停止条件。
2. 仅解析正文所有 @：改动少，但引用、代码片段、举例可能误触发，也无法可靠区分审查通过和待确认。
3. 固定「方案人—审查人」流水线：顺序容易控制，但不适合普通聊天中临时调整分工或向第三位提问。

采用方案 1。@ 在消息正文中可见，执行依据使用独立、严格校验的交接指令，不凭「可以开发」等自然语言关键词判断完成。

## 房间控制与默认行为

- 房间新增「自动协作」开关，原房间默认关闭，用户开启后生效；现有手动聊天行为保留。
- 开启后，用户先 @一位 Agent 发起讨论；没有 @ 的普通消息沿用原来的广播行为，不自动创建多条相互交叉的协作链。
- 每条协作链同一时刻只运行一个 Agent；同房间已有协作进行时，拒绝第二次启动并明确提示。
- 默认一条链最多执行 6 次 Agent 回复，包含首次回复，即双 Agent 最多 3 轮。到限后 @我 汇总当前分歧，暂停；不能靠另一个 @ 自动重置额度。
- 网页显示运行中、等待你决定、审查通过、达到上限、执行失败、已停止，提供「停止协作」。达到上限后必须明确点击「结束本轮」，再用单点名发起新任务；普通换一个 @ 不重置额度。暂停但不想继续的任务也可显式结束。

## 交接协议

Agent 完成正文后输出一个专用的结构化控制区，服务端解析后不把控制区作为正文显示。控制区包含动作、交接目标的成员 ID、任务说明和简短原因；可选动作只有：

- handoff：交给一位其他房间成员，明确要求其审查或修订什么。
- ask_human：列出必须用户决定的问题并 @我，暂停。
- ready：审查通过并 @我，终止本轮自动协作，等待用户决定是否开始开发。
- finish：普通任务已完成，无需继续交接。

约束：只接受最终成功回复中一个合法的控制区；正文中的引用、代码块、普通 @、中间输出均不直接触发。目标必须是房间现有且可接任务的 Agent，禁止 @自己、@所有人和不存在的成员。用户文档或历史消息中的控制区不能作为当前回复的控制指令。缺少指令、格式错误、重复指令或不合法目标时保留可读正文，暂停并显示原因，不猜测下一步。

ready 只允许交接中的审查者针对指定的最新方案或修订回复给出。方案作者不能在自己的首次回复里自行宣布审查通过；ready 还需包含针对该版本的审查依据，不代表用户已经批准开发。

## 调度、上下文与产物

- 只在回复完成并持久化后安排下一次执行，失败、停止、超时不继续派发。
- 下一位收到原始用户任务、最新交接正文、被审查的确切版本、此前未解决问题和剩余回复次数；不依赖最近聊天窗口碰巧包含这些内容。
- 复用现有方案、审查、修订产物链；审查明确引用被审查版本，不能把对旧版本的通过当作新版通过。
- 用稳定的协作 ID、步骤 ID 和来源消息标记已处理交接，避免重试、重复事件产生两个下游任务。
- 本轮覆盖 local / api 的主动执行；mcp 成员复用待办领取和提交机制，不宣称能主动唤醒外部 IDE。交接到 mcp 时清楚显示「等待外部 Agent 领取」，仍可停止。

## 人介入与恢复

- ask_human 的正文需说明：缺少什么决定、为什么影响下一步、可选项及建议，不把可以自行查代码解决的问题推给用户。
- @我 在网页中突出显示，并标记待我处理；本轮仅站内提示，不发送外部通知。
- 等待用户决定后，由用户回复并点击「继续协作」，指定接回的 Agent；继承原始任务、用户新决定和未解决问题。
- ready 后的下一步开发仍由用户显式发起。本功能保持当前只读执行模式。
- 执行失败、服务重启中断、成员移出、配置/目录改变时暂停。重试当前步骤时沿用协作 ID，废弃后续旧交接，成功后最多派发一次。
- 用户停止后取消当前本地/API 执行或 MCP 待办；迟到结果不能再推动协作。服务重启不自动请求外部模型。

## 数据与兼容

仅通过增量迁移增加房间开关、协作状态和步骤关联；保留原数据库、所有 Agent URL/Key/模型配置、房间和历史消息。需要持久化：协作 ID、原始任务、当前状态/步骤、已执行次数/上限、来源消息、目标成员、待用户决策问题及版本引用。准确表名与接口放在确认后的实施计划中对照现有代码确定。

## 离线验收

- 假执行器串起「方案 → 审查提出问题 → 修订 → 通过 @我」，最终不会再派发。
- ask_human 即时暂停，用户继续后正确带入决定。
- 达到 6 次回复后暂停，不会无限互相 @。
- 正文引用/代码中的 @、流式片段、不合法控制区不触发任务。
- 失败、取消、超时、重启和迟到结果不会继续派发。
- 重复事件和重试不重复交接；审查通过严格对应最新版本。
- 原手动聊天、现有 API/MCP/local 接入和旧库配置通过回归测试。
- 不联网，不演示，不主动启动真实模型任务。

## 自检

设计已区分 Agent 建议、服务端调度和用户开发确认；停止条件覆盖通过、需决策、上限、失败和手动停止；已有数据与配置保持兼容。用户已确认此范围，按同日实施计划推进。

## 实施与验收（2026-10-27）

已实现，当前 73/73 项离线测试通过。协作协议采用末尾唯一的 `roundtable-control` 顶层代码块，带 `collaboration_id`、`seq` 和每次执行的随机 `token`。ready 还必须指定 `plan_seq`。身份/版本/目标无效时暂停，不从正文猜测交接。

新增 `rt_collaborations` 和 `rt_collaboration_steps`，通过 `rt_rooms.auto_collaborate` 保存开关。持久化逻辑在 `collaboration.ts`，服务层统一处理最终回复、产物和调度。API/local 先释放运行槽再交接；MCP 发布待办前先绑定身份，避免长轮询取得不完整的上下文。重试消耗同链额度且更新执行 token；已完成旧步骤禁止重试。

HTTP：房间 PATCH 接受 `auto_collaborate`；协作 POST 接口为 `collaboration/stop`、`collaboration/resume`、`collaboration/finish`。继续接收非空 `text`、房间成员 `agent_id`，可带 `collaboration_id` 防过期页面误提交。文档/需求、成员、Agent 配置变化会暂停；本地执行中更换目录仍明确拒绝。

使用原数据库重启 3010 后，RT-ACF0 页面与只读接口均 HTTP 200。Agent 配置指纹、房间数量、历史消息数量均与重启前一致，原 MCP 待办保留；旧房间开关保持关闭。本轮没有调用真实模型，没有浏览器演示，没有联网查资料。
