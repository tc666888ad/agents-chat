## 0. 结论摘要

这份文档的质量在同类立项材料里属于中上：它把"为什么做"和"为什么不用现成方案"都写了，有显式取舍（1.4 节承认会话被占用）、有范围边界（12 节）、有可反驳的验收标准（13 节）、有待验证清单（14 节）。这些是很多人写不出来的。

但它的三个 P0 问题都发生在**地基**上：

| 级别 | 问题 | 不解决的后果 |
|---|---|---|
| P0-1 | `wait_messages` 长轮询被当成唯一的、默认的接入方式 | 模型自行收尾 + 客户端超时 + 双方在线窗口窄，产品的高光路径大概率跑不通 |
| P0-2 | `join_room` 只下发需求，不下发工程上下文 | 两个 agent 只能谈出"看起来很合理、两边都实现不了"的接口 |
| P0-3 | 价值主张是"字段对齐"，但那是代码生成能解决的事 | 验收标准不可测，产品价值不可证，立项叙事站不住 |

P1 有 6 项（影响产出质量和体验的核心能力缺失），P2 有 10 项（流程与规则漏洞）。建议按本报告第 9 节的改动清单逐节修改文档，再进入实现。

---

## 1. 总体评价

### 1.1 做对的地方

1. **问题定位准确**。"把联调时才发现的问题提前到设计阶段"是一个真实、可感知、有明确经济账的痛点，比"AI 辅助开发"这类含糊叙事强。
2. **做了方案对比**（1.5 节）。明确指出 Claude-Bridge 只能传消息、mcp_agent_mail 缺鉴权，这说明作者看过现场，不是凭想象设计。
3. **承认了最关键的取舍**（1.4 节末）：会话被占用、需要人在旁边看着、不做后台常驻。这种"把代价写在纸面上"的习惯值得保留。
4. **规则在服务端强制**（第 6 节工具集 + 5 节状态机）。这是与"两个 agent 互相发消息"类玩具的本质区别：`approve` 必须是最新版本、有阻塞 issue 时拒绝确认、旧 `base_version` 拒绝提交，这些约束放在服务端而不是提示词里，方向完全正确。
5. **`wait_messages` 返回"下一步提示"**（6 节末）。这是个很小但很真实的细节，说明作者理解 agent 会跑偏。
6. **待验证事项单列**（14 节）。愿意写"我还没验证"的文档，可信度天然更高。

### 1.2 主要问题（三个层面）

- **架构层**：把"如何让 agent 持续在线"当成了前置难题，而这个难题的收益（自动化协作）与代价（兼容性、等待、上下文消耗）不成比例。见 P0-1。
- **产品层**：把"字段对不对"当成了核心价值，而"字段对不对"恰好是 OpenAPI 生态已经解决得最好的部分。真正的价值在语义与边界，文档没有把这个抓手设计出来。见 P0-2、P0-3。
- **流程层**：状态机和规则覆盖了 happy path，但对"最后一刻漂移""谈不拢""issue 卡死""人只能驳回不能改"这些真实会天天发生的分支没有设计。见第 4 节。

## 2. P0：写代码前必须改掉的三件事

### P0-1 长轮询不应当是默认传输方式

**现状**：1.4 节将 `wait_messages`（阻塞 50 秒）定义为"核心技术难点"的解法；6 节把它做成唯一的消息接收工具；14 节把"客户端超时上限""agent 是否会自行停止"列为"待验证"。

**问题**：这三个"待验证"项其实是同一个假设——"模型愿意且能够稳定地挂在一个阻塞调用上"——的三条证据，而这个假设很可能不成立：

1. **模型会自行收尾**。连续两三次返回"暂无新消息"，多数模型的自然反应是总结一下并结束回合（"我先在这里等，有新消息再处理"），而不是继续调用。靠提示词约束可以缓解，但"需要多少提示词才能稳定循环"本身是不可控的（这正是 14 节的第 3 条）。
2. **客户端超时不归你管**。MCP 规范没有对工具调用时长做强约束，但各客户端和中间代理有各自的空闲超时（常见 30s / 60s 量级）。50 秒是一个在很多客户端上会踩线的数字，失败表现是"工具报错"而不是"等待中"。
3. **双方在线的窗口很窄**。长轮询要发挥作用，两边的 agent 必须同时处于循环里。而 1.4 节自己写了"开发者在旁边观察，必要时提示继续"——如果人都已经在旁边了，长轮询实际节省的只是"人打一句话"的成本，却引入了兼容性风险和 12 分钟的纯等待（50s × 15 轮）。
4. **上下文重复消耗**。每被唤醒一次，agent 都要重新读一遍房间上下文。15 轮下来是 15 次重复，14 节第 4 条已经意识到这个问题。

**建议**：把"消息投递"与"agent 唤醒"解耦。服务端只负责三件事：房间状态、单调游标、消息列表。工具签名改为带参数的非阻塞优先设计：

```
poll_messages(cursor, wait_ms = 0)   // wait_ms = 0 立即返回；> 0 阻塞至多 wait_ms
join_room(room, role, client?)       // 返回 profile、状态、当前契约、游标、最近 N 条
```

服务端对 `wait_ms` 设上限（建议 30s，不要 50s），并且**无论是否有消息，都返回明确的 `has_more` 和 `next_cursor`**，让"继续轮询"成为一个有依据的决策而不是猜测。

然后提供两种接入模式，服务端不做区分：

| 模式 | 触发方式 | 定位 | 对客户端的要求 |
|---|---|---|---|
| **回合制（默认）** | 人一句话触发："去 ORDER-0142 看有没有新 issue" | 稳定、可重试、每次调用都是边界清晰的短任务 | 只要会发 HTTP 即可，MCP 都不是必须的 |
| **在线托管（增强）** | agent 自己循环 `poll_messages(cursor, 30000)` | 体验更自动，作为跑通后的增强 | 需要客户端支持长耗时工具调用 |

关键论点：**回合制不是退化，它恰好匹配真实使用方式**。人本来就在旁边看着（1.4 节已确认），每次被触发的 agent 上下文干净、任务明确、失败可重试。而且它对客户端零假设，彻底兑现 1.3 节"不限定 agent 类型"这条约束——连"必须支持 MCP Streamable HTTP"都不再是硬要求，这对 Codex / Cursor 这类支持程度参差的客户端是决定性的。

**文档改法**：

- 1.4 节：把"核心技术难点"从"agent 不会主动听"改为"**如何在不假设 agent 常驻的前提下，让多个 agent 围绕一份契约推进**"；把长轮询降级为"在线增强模式"。
- 6 节：工具表增加 `poll_messages`，`wait_messages` 改名并参数化；"wait_messages 行为"小节整体重写。
- 12 节：MVP 范围里，"长轮询"从必选改为"可选（在线模式）"。
- 13 节：验收第 2 条"长轮询稳定往返不少于 15 轮"改为"回合制下完整走通一次协商"，长轮询单独作为增强模式的验收。

### P0-2 `join_room` 必须下发工程上下文，而不只是需求

**现状**：4 节第 2 步，`join_room` 返回"需求、协商规则、历史消息、当前契约"。全篇没有提到"现有代码约定"。

**问题**：两个 agent 手里只有一份 PRD 文本。前端 agent 不知道现有请求封装、错误处理中间件、组件库的数据结构偏好；后端 agent 不知道现有领域模型、表结构、鉴权方式、错误码体系、分页惯例。这个条件下产出高质量契约的概率很低，更常见的结局是：

- 谈出一套"政治上正确、工程上孤立"的新风格（比如新建一个和现有响应包装不一致的结构）；
- 或者两边各自脑补，看似达成一致，实现时才发现一个用 cursor 分页、一个用 page/size。

**建议**：`join_room` 除了需求，还下发一份**团队约定基线（profile）**，按团队维护一次、每个房间挂载。它在提示词里是硬约束，不是参考：

```yaml
# team-profile.yaml
response_envelope: { code: int, message: string, data: T, trace_id: string }
pagination: { style: page_size, params: [page, page_size], returns: [list, total, page, page_size] }
error_codes: { scheme: "HTTP + biz_code", doc: "docs/error-codes.md", unknown: "500000" }
auth: { scheme: bearer, unauthenticated: "401 + code 401001" }
formatting: { time: "RFC3339 +08:00", money: "integer cents", id: "string snowflake" }
naming: { json: camelCase, path: kebab-case, query: camelCase }
existing_entities: [Order, OrderItem, Payment]     # 摘要即可
sample_endpoints: [ "GET /api/v1/orders" ]          # 片段即可
```

提示词模板固定一句："**以上为硬约束。若需求与约定冲突，必须显式提出冲突，不得静默绕过。**"

**顺带的产品价值**：这份 profile 本身就是可复用资产（团队接口规范库）。它比"让 agent 每次重新谈一遍"高效一个数量级，而且是这个产品最容易形成护城河的部分——规范沉淀得越多，协商质量越高。

**文档改法**：4 节新增 4.0"团队约定基线"；6 节 `join_room` 返回项增加 `profile`；12 节 MVP 范围增加"团队 profile 的维护与挂载"。

### P0-3 价值主张需要收窄：从"字段对齐"到"歧义挖掘 + 契约治理"

**现状**：1.1 节的痛点是"接口少字段、结构不对、分页或枚举约定不一致"；1.2 节的解法是"两个 agent 协商字段和结构"；13 节第 4 条承诺"联调阶段不再出现字段缺失或结构不一致问题"。

**问题**：这条痛点链里，**最容易被工具吃掉的部分被当成了产品核心**。少字段、结构不对、枚举不一致，用 OpenAPI + Spectral + 从契约生成 TS 类型/Mock 就能解决大半，不需要两个 agent 聊天。而且 13 节第 4 条既不可测、又是在承诺一个代码生成器就能做到的事——如果这是产品的核心承诺，那这个产品没有存在必要。

**真正需要协商、且工具无法自动化的部分**（也是返工的真实来源）：

- 业务语义：这个状态字段的"已完成"到底包不包含退款中
- 边界条件：空列表、超大分页、部分失败、超时后的幂等
- 错误码语义：这个 4xx 前端该弹什么、该不该重试
- 分页语义：游标还是页码，游标失效怎么办
- 权限矩阵：未登录 / 无权限 / 数据不存在分别返回什么、是否可枚举
- 并发与幂等：重复提交、乐观锁、幂等键
- 异步与回调：哪些操作用异步 + 轮询/Webhook，超时策略
- 精度与时区：金额、汇率、跨时区时间
- 状态机的合法迁移与非法迁移的错误码

**建议的新表述**（可直接替换 1.2 节首段）：

> 把联调时才暴露的问题提前到接口设计阶段：让前后端 agent 围绕同一份需求，把**规格层面的歧义**（语义、边界、错误码、权限、并发、精度）在写代码前挖出来、逐条收敛并留痕，冻结成一份双方确认、可被机器校验的契约；冻结之后，契约的每一次演进都是可控、可审计的。

**文档改法**：1.1 节把"字段缺失"从主痛点降为举例；1.2 节替换为上段；4.1 节审查清单按上面 9 类扩充（现有的 8 条偏"字段级"，缺语义和并发）；13 节第 4 条重写（见第 6 节）。

## 3. P1：影响产出质量与体验的六项

### P1-1 `understanding` 阶段要有结构化产物：供需矩阵

**现状**：4 节第 3 步，双方各发一条 `understanding` 消息，"先对齐理解再谈字段"。

**问题**：两条自然语言消息无法被校验、无法被 diff、无法指出缺口。协商阶段于是退化成逐字段试探。

**建议**：把理解阶段变成结构化提交：

- 前端提交 `views[]`：`{ name, route, interactions[], needs[] }`，`needs` 是"我需要在某个页面上展示/提交的字段与语义"。
- 后端提交 `entities[]`：`{ name, source, fields[], constraints[] }`。
- 服务端据此生成**供需矩阵**：每个 `need` → 被哪个 `entity.field` 或哪个接口路径供给；缺口高亮为"未供给"，冲突高亮为"语义不一致"。

这张矩阵是协商的真正抓手，也是最值得放在网页首屏的东西——比 diff 直观得多，人一眼就能看出"这个页面要的字段后端根本没有"。它同时天然解决了"issue 定位到哪个 pointer"的问题（从矩阵格跳转）。

**文档改法**：4 节第 3 步重写；6 节新增 `submit_understanding(payload)` 工具；6.1 节消息类型增加 `understanding` 的结构体定义；9 节网页增加"供需矩阵"视图。

### P1-2 人的角色要从"旁观 + 插话"升级为"决策点"

**现状**：3 节，人能"旁观、插话、裁决问题、冻结和重开房间"。

**问题**：这只是"人在场"，不是"人参与"。真实协商中最有价值的是人在**分叉点拍板**（"这个聚合字段后端给不了，是拆两次请求还是加聚合接口？"），而现在的设计里，agent 只能连续追问、或者自己替人做决定。

**建议**：新增 `request_decision` 工具：

```
request_decision(question, options[{id, label, tradeoff}], blocking = true)
```

- 服务端把它渲染成网页上的一个待决卡片（A / B / 自定义）。
- 人选择后，作为 `decision` 类型消息回到 `poll_messages`，agent 拿到明确答案继续。
- 未决期间，房间状态标记"待人决策"，并进入全局待办队列。
- 决策结果写进契约的 `x-decisions` 扩展字段，冻结时一并留档——这是审计链上最有价值的一段。

这个能力比"人就着消息流打字插话"结构化得多，也更容易做成产品的核心交互。

**文档改法**：3 节人的职责重写；6 节新增工具；9 节房间页增加"待人决策"区域。

### P1-3 人必须能直接编辑契约

**现状**：9 节人的操作只有"发言、裁决 issue、驳回、冻结、重开"。

**问题**：如果只是字段名写错、某个 description 有歧义、枚举少一个值，人要反过来用自然语言指挥 agent 改，再等它提交一版——成本远高于自己改两行。而"最终拍板权"如果没有"直接修改权"作为兜底，就只是"驳回权"。

**建议**：网页提供契约编辑器（Monaco + OpenAPI schema 校验 + Spectral 即时提示），人保存时生成 `author=human` 的新版本，同样走双方确认流程（或者由人显式声明"此版免确认"，但这应该留痕）。人的修改本身也是一条 `system` + `human_edit` 消息，agent 下一轮必须看到。

**文档改法**：3 节人说"可编辑契约"；8 节版本记录增加 `author_type: agent | human`；9 节操作列表增加"编辑契约"。

### P1-4 `approve_contract` 需要结构化，不能是一个点击

**现状**：6 节，`approve_contract(version)`，参数只有一个版本号；11 步流程里"双方都对该版本调用 approve"。

**问题**：一个只带版本号的确认，太容易变成 agent 的"顺手动作"——尤其是在长轮询循环里，"看到 v3 没有 blocking issue 就 approve"几乎是必然行为。那 1.5 节选择自建方案的核心理由（"强制双方确认才能冻结"）就被架空了。

**建议**：确认必须携带结构化结论：

```
approve_contract(version, checklist[{item, verdict, note}], open_suggestions[], readiness)
```

- `checklist` 对应 4.1 的审查清单，逐项 `pass / fail / n/a`，`fail` 时不允许 approve。
- `open_suggestions` 要求列出已知的非阻塞遗留项（允许为空，但必须是显式空），冻结时随契约存档。
- `readiness` 表示"我这边 mock / 类型 / 契约测试是否已就绪"。
- 记录 `approved_by: { user, agent, at }`，并在网页标注"agent 代确认，人未复核"。

这样"双方确认"才是一个有内容、可审计的事件，而不是一个布尔值。

**文档改法**：6 节工具定义；8 节 approvals 表结构；13 节验收第 3 条增加"缺少 checklist 或含 fail 项的 approve 必须被拒绝"。

### P1-5 冻结即资产：不可变引用 + 自动影响面

**现状**：8 节"冻结版本不可修改，只能通过重开产生新版本"；4 节第 8 步"agent 把契约写入各自仓库"；第 9 步"人重开房间，产生新版本"。

**问题**：冻结产物没有稳定标识，代码里怎么引用它？重开之后，怎么知道哪些已实现的代码受影响？这两件事不做，"契约"就只是一份聊天记录的快照，而不是可以被 CI、被代码、被测试引用的资产。

**建议**：

- 冻结时生成不可变引用：`ORDER-0142@v4#sha256:abc123…`，网页、CLI、API 都返回它；前端类型生成、后端契约测试、Mock 服务器全部 pin 这个引用。
- 重开时，服务端自动计算相对冻结引用的 **breaking change 列表**（用 `oasdiff breaking`），并把结果作为"影响面"推给双方 agent 和人。
- 提供 `GET /rooms/:code/contracts/:ref`（按引用取，而不是按"最新"取），保证幂等。

这条把产品从"聊天工具"抬到"契约治理"，也是唯一能自然接到 CI 的地方。

**文档改法**：8 节新增"冻结引用"与"影响面"；5 节 `frozen → negotiating` 边上补"自动产出 breaking change 报告"；12 节"暂不包含"里的"CI 集成"可以保留，但"按引用取契约"必须进 MVP。

### P1-6 "下一步提示"用状态模板生成，不要用模型生成

**现状**：6 节末，"返回内容附带一句下一步提示，例如'对方提交了 v3，请按清单审查'"。

**问题**：如果这句话是模型生成的，同一状态会给出不同的引导，agent 行为不可复现，出了问题也没法归因。

**建议**：由房间状态 + 角色 + 待办项确定性生成（查表），并且**同一状态下措辞固定**。可测试：给定状态 → 期望提示文本。

**文档改法**：6 节加一句"提示文本由状态机确定性生成，不含模型生成内容"。

## 5. 技术实现的调整建议

1. **`poll_messages` 参数化**（见 P0-1）。服务端封顶 30s；返回体固定含 `has_more`、`next_cursor`、`server_time`。提供 `wait_ms=0` 的纯拉取，兼容性最好。
2. **游标用 SQLite 事务保证**。`messages.seq` 用 `INTEGER PRIMARY KEY AUTOINCREMENT`，写入在 `BEGIN IMMEDIATE` 事务内完成；不要用进程内计数器（agent、人、system 三源并发）。同时把"分配 seq"和"插入消息"放在同一事务，避免出现空洞导致 agent 误判丢消息。
3. **SSE 要支持 `Last-Event-ID`**。断线重连是网页端的常态（切标签页、休眠），用 seq 直接作为 event id，重连即从 seq+1 补发。
4. **单进程的并发假设要写清楚**。每个在线 agent 占一条长连接、每个网页占一条 SSE。按 `团队人数 × 2 + 网页数` 估算连接数，SQLite 开 WAL，写操作用单写队列串行化。如果在线模式被大量使用，这个模型会先撞上连接数而不是 CPU——建议在 10 节写一句容量假设。
5. **`propose_contract` 同步返回可执行的校验结果**，而不是只返回"通过/不通过"：
   - `lint`: Spectral 结果（`severity`、`pointer`、`message`、`rule`）
   - `diff`: 相对 `base_version` 的结构化变更 + `oasdiff` breaking 列表
   - `rules`: 违反 profile 的项（如分页参数名不符合约定）
   agent 拿到这份结构化结果，比拿到一句"校验失败"有用得多；这也是"服务端强制规则"真正落地的地方。
6. **token 分级**：`viewer`（只读、可发言）/ `member`（可 propose、可 approve）/ `admin`（可冻结、重开、管理 profile）。approve 与 freeze 分属不同权限，避免 agent 持有的 token 顺带拥有冻结权。
7. **`get_contract` 支持按引用取**（见 P1-5），并对冻结版本返回内容 hash，便于客户端校验完整性。
8. **建议 10 节补一句存储边界**：PRD 文本、契约、消息都是公司 IP，SQLite 单文件 + Docker volume，备份策略在部署阶段给出（哪怕只是一句"每日 SQLite backup"）。

## 6. 验收标准重写（可直接替换 13 节）

原文第 4 条不可测、第 1 条时间过于乐观。建议改为：

1. **流程可达**：两台机器、两种不同 agent，用一个真实需求完成"入场 → 理解 → 协商 → 双方确认 → 人工冻结 → 写入各自仓库"。时间不作硬指标，但需记录实际耗时作为基线。
2. **协商有产出**：冻结契约中，至少 N 条问题可追溯到 `raise_issue` 或 `request_decision`（N 由首次试点确定，建议 ≥5），且每条都有结论。用来证明"协商真的抓到了东西"，而不是走过场。
3. **规则强制有效**：服务端必须拒绝以下操作，并返回可读原因——未通过 lint/profile 校验的契约、基于旧 `base_version` 的提交、对旧版本的确认、存在 blocking issue 时的确认、`pending_freeze` 期间的新提交、缺少 checklist 或含 `fail` 项的 approve。
4. **质量可观测**（替换原第 4 条）：试点需求从冻结到联调结束期间，**契约变更次数 ≤ 1**、**因接口语义产生的返工工时记录为 0**、**首次联调接口通过率 ≥ 90%**。这三个数字比"不再出现字段不一致"可测，也更接近真实价值。
5. **可恢复性**：长轮询/SSE 断线后，双方都能凭游标无损补齐消息（至少验证 3 次随机断线）。

另外建议产品自身埋点（不对外承诺，但立项要看）：房间数、平均协商轮次、平均冻结时长、blocking issue 占比、冻结后 breaking change 次数、待人裁决平均等待时长。

## 7. 立项叙事：补一页"和现有工具的关系"

文档目前没有回答一个问题，而它在立项会上一定会被问：**"为什么不用 Apifox / YApi + 人工评审？"**

建议在文档开头（1.5 节之前）加一节，把边界讲清楚：

- **已经有成熟工具的**：接口文档托管与 Mock（Apifox / YApi）、契约 diff 与变更通知（Bump.sh 一类）、契约驱动的 CI 门禁（Optic 一类）、从契约生成 SDK（Stainless / Speakeasy 一类）。这些不要重做，能接就接。
- **没有人做好的**：让**两个不同机器上的 agent**，在**服务端强制的规则**下，围绕同一份契约**对抗式协商**，并把每一次分歧、裁决、确认完整留痕。
- **本产品的差异点一句话**：不是"更好的接口文档平台"，而是"**接口契约的协商与治理层**"——agent 原生参与、规则在服务端强制执行、全过程可审计、不离开开发者终端。

配套要做的取舍说明：正因为不做文档托管、不做 Mock 托管、不做代码生成，才能把"协商与治理"做深。这也是 12 节"暂不包含"那些项的理论依据，建议在 12 节补一句这个逻辑。

## 8. 一周验证计划（不写产品代码）

在动工前，用三个 spike 证伪或证实关键假设。每个 spike 都要有明确的判定标准，避免变成"试了一下感觉还行"。

### Spike 1：客户端长耗时工具行为（0.5–1 天）

- 目标：回答 14 节前三条待验证事项。
- 做法：写一个 60 行的 MCP server，只提供一个 `sleep_and_return(seconds)` 工具。在 Codex、Claude Code、Cursor 上分别调用 30s / 50s / 90s，观察：是否超时、报什么错、模型在连续 3 次空返回后是否继续调用。
- 判定：若 3 个客户端里有 2 个在 50s 内失败，**在线托管模式不进 MVP**（P0-1 的建议即成立）；若都能稳定跑，长轮询可以保留为默认，但仍建议保留回合制入口。

### Spike 2：协商有没有用（2–3 天，最重要）

- 目标：验证"两个 agent 协商"本身是否产出优于"后端直接写"的契约。
- 做法：选一个真实需求。手写一份 `team-profile.yaml`（P0-2 的样例即可），让后端 agent 起草 v1，前端 agent 只带 profile + PRD 做一次回合制审查（raise issues），后端回复一轮。全程人工记录。对照组：同一个后端 agent 不看前端意见，直接产出契约。
- 判定：前端 agent 提出的问题里，有多少是"人看了会认同、且确实会在联调阶段暴露"的？若少于 30%，说明提示词和清单需要重做，而不是去做长轮询。
- **这个 spike 的结果决定项目要不要继续**，优先级高于任何工程实现。

### Spike 3：供需矩阵是否可自动化（1 天）

- 目标：验证 P1-1 的可行性——能否让前端稳定产出 `views[].needs`、后端稳定产出 `entities[].provides`，并自动匹配出有意义的缺口。
- 做法：给两个 agent 一个固定的 JSON Schema 做结构化输出，跑 2–3 个需求，人工评估矩阵缺口的质量。
- 判定：若缺口准确率低，退化为"矩阵只作为人的辅助视图，不做自动校验"，MVP 相应收缩。
